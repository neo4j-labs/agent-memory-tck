# Reuse application HTTP clients through a published transport seam

Applications configure their HTTP clients with observability (Spring observations and tracing, LangChain4j request logging) and network policy (proxy, TLS, timeouts, connection pooling), and memory calls should inherit both. The Java client therefore sends every NAMS exchange through an `HttpTransport` seam. Four built-in adapters implement it: the JDK `java.net.http.HttpClient`, which remains the default, Spring Framework `RestClient` and `WebClient`, and LangChain4j `dev.langchain4j.http.client.HttpClient`. An application that uses any other HTTP client implements the seam itself. This supersedes [ADR 0005](0005-use-jdk-http-without-a-transport-extension.md)'s prohibition of a transport seam and of injecting a configured client. ADR 0005's decisions against automatic retries and against a `MemoryClient` lifecycle method remain in force.

`HttpMemoryClient`, formerly `JdkMemoryClient`, continues to own routes, authentication, JSON processing ([ADR 0003](0003-optional-internal-json-adapters.md)), status and failure mapping ([ADR 0006](0006-use-client-owned-exceptions.md)), operation logging ([ADR 0021](0021-observe-operations-without-exposing-content.md)), and live-handle construction. The seam has one asynchronous operation. It sends a method, an absolute URI template with UUID or integer variables, headers, and a `Body`, and it returns the status, case-insensitive multi-value headers, and body bytes without interpreting the status. The core sends either `NoBody` or `ByteArrayBody`. `Body` stays open to other implementations, such as a streaming body, so carrying one later does not require a new SPI type. `org.neo4j.agentmemory.http` is the published SPI package: `HttpTransport`, `HttpCall`, and `HttpResult`. `HttpMemoryClient` shares the package but is not part of the SPI; it is built only from a `MemoryClientConfiguration`, so it adds no route around `MemoryClient.create(...)`. The built-in adapters live in `org.neo4j.agentmemory.http.internal` and are not part of the SPI. An earlier version of this decision kept the seam internal because no code outside the artifact needed to implement it, and because publishing later breaks nobody while withdrawing a public SPI is a breaking change. That was reversed: an application on OkHttp, Apache HttpClient, Vert.x, or another client should be able to bring its own HTTP transport and keep its observability and network policy, rather than wait for a built-in adapter or give both up. The artifact is unreleased, so no stability promise is made for the SPI yet. One `MemoryClient` implementation per framework remains rejected because it would duplicate route, failure, and logging code.

A custom transport must:

1. return from `send` without waiting on I/O, running a blocking client's exchange on an application executor;
2. complete with an `HttpResult` for every HTTP response, including 4xx and 5xx, so that `HttpMemoryClient` can map it to `MemoryServiceException`;
3. send to `call.uri()` with `call.headers()`, which take precedence over any same-named header the wrapped client would add; anything else the wrapped client contributes, such as default headers, cookies, or interceptor headers, is the application's choice;
4. send `NoBody` as no request body, and the `body()` bytes of any other `Body` unchanged;
5. perform no retries and never close the wrapped client or executor;
6. treat cancellation as best effort; and
7. report a short, nonblank, kebab-case `name()` that does not reuse a built-in name.

A custom transport does not translate its own failures: an exception thrown by `send`, an exceptionally completed future, or a null future becomes a `MemoryClientException` that retains the cause. The README describes the extension point and this contract in prose, without a worked example. No reusable conformance kit is published for third-party transports.

The memory client does not strip what an application's client adds to a request. An application that configures default headers, cookies, a default API version, interceptors, or exchange filters on the client it injects is assumed to know that they apply to memory requests too. Only the memory headers take precedence, because NAMS rejects a request without its own `Authorization`, `Accept`, and `Content-Type`. Precedence is applied per request rather than by cloning the application's client and replacing its defaults: in Spring, a header replaced on a cloned client's defaults still loses to the application's `defaultRequest`, and the JDK and LangChain4j clients have no defaults to replace.

Applications pass an already built client to `MemoryClientConfiguration.Builder` through `jdkHttpClient(HttpClient)`, `restClient(RestClient, Executor)`, `webClient(WebClient)`, or `langChain4jHttpClient(HttpClient, Executor)`, or a custom transport through `httpTransport(HttpTransport)`. The client setters need distinct names because javac 17 must resolve the parameter types of every same-name, same-arity overload, so overloads naming different frameworks fail to compile when any of them is absent. Setters reject null immediately and the last setter called wins. An omitted client falls back to a new `HttpClient.newHttpClient()`, created when the configuration is built and shared by every client created from that configuration. `MemoryClient` keeps only `create()` and `create(MemoryClientConfiguration)`. The builder accepts built clients rather than framework builders so the library never mutates application configuration, and the library never closes an injected client, executor, or transport. The configuration remains the only source of the base URL and the Workspace API key, and requests use absolute URLs, so a Spring client's base URL does not apply. Everything else the application configured on a Spring client does, including default headers, cookies, `defaultRequest` customizations, and a default API version; a path-segment API version inserter therefore rewrites memory URLs too. Reflecting over the builder's methods fails with `NoClassDefFoundError` unless every framework is present; this is accepted because applications call the builder rather than introspect it.

`RestClient` and LangChain4j block the calling thread, so their setters require an application `Executor`. `WebClient` does not block and needs none. The JDK client runs dependent work on its own executor, which applications configure through `HttpClient.Builder.executor(...)`. Operation futures are dependent stages of the transport's future, so cancelling one does not cancel the exchange for any transport; propagating cancellation to the transport is left to a later decision. The Spring adapters use `exchange(...)` and `exchangeToMono(...)`, so status handlers registered on the application's client do not apply and non-success responses keep their headers. The `WebClient` adapter reads response bodies through the client's codecs, so the application's in-memory buffer limit, 256 KB by default in Spring and `spring.codec.max-in-memory-size` in Spring Boot, bounds memory responses; a larger response fails the transport phase with a `MemoryClientException` caused by `DataBufferLimitException`. LangChain4j throws `HttpException` for non-success statuses and discards the response headers, so its `MemoryServiceException` carries the status and body excerpt with no headers or content type, and its operation events omit the request ID. This loss is documented, and the Spring adapters are recommended when those diagnostics matter. Every exception raised by a transport, including executor rejection and a synchronous failure inside the transport, completes the returned future exceptionally with a `MemoryClientException` that retains the cause. Building a transport request therefore no longer throws synchronously; [ADR 0023](0023-build-validated-client-configuration.md)'s base URL validation makes the previous synchronous case unreachable through the public API.

Route templates reach `RestClient` and `WebClient` so that Spring observations tag `uri` with a template such as `/v1/conversations/{conversationId}` instead of `none`. Operation events move from the `org.neo4j.agentmemory.JdkMemoryClient` logger to `org.neo4j.agentmemory.MemoryClient`, and `event=client.initialized` reports `transport=jdk-http`, `spring-rest-client`, `spring-web-client`, `langchain4j-http`, or a custom transport's name. The rename breaks existing logger configuration, which is acceptable before 1.0.

`spring-web`, `spring-webflux`, and `langchain4j-http-client` are optional dependencies of `agent-memory-client`, in the same way as Jackson. The core still runs without any of them. The Spring floor is Framework 7.0.0 for both Spring adapters, following the Spring AI 2.x line: Spring AI 2.0.0 resolves to Spring Framework 7.0.8, Spring Boot 4.1.0, Jackson 3.1.4, and Java 17 bytecode. Spring 6.x is unsupported, partly because Spring 7 stopped implementing `MultiValueMap` in `HttpHeaders`. The `WebClient` adapter is verified on the Reactor Netty connector that Spring Boot WebFlux applications use. The LangChain4j floor is 1.0.0, which already provides every API the adapter uses. Verification covers the floors and Spring Framework 7.0.9 and LangChain4j 1.22.0. Framework wiring such as Spring Boot auto-configuration or a LangChain4j `ChatMemoryStore` remains downstream, as recorded in [ADR 0007](0007-keep-agent-workflow-orchestration-outside-core.md) and [ADR 0014](0014-keep-java-client-within-hosted-service-boundary.md). The [ADR 0013](0013-validate-traffic-against-published-openapi.md) contract suite runs once for each built-in adapter.

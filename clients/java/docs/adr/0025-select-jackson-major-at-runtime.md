# Select Jackson 3 or Jackson 2 at runtime

Spring AI 2.x brings Jackson 3 while LangChain4j brings Jackson 2, so requiring Jackson 3 forces a second mapper major into every LangChain4j application. The client therefore ships internal `Jackson3JsonCodec` and `Jackson2JsonCodec` adapters in the single `agent-memory-client` artifact, declares both `tools.jackson.core:jackson-databind` and `com.fasterxml.jackson.core:jackson-databind` as optional dependencies, and selects a codec from the runtime classpath on each `MemoryClient.create(...)`. This refines [ADR 0003](0003-optional-internal-json-adapters.md), which anticipated the second adapter and the Jackson 3 preference.

Selection tries Jackson 3, then Jackson 2. A codec is usable when its `JsonMapper` class is present and the adapter builds its mapper; a `LinkageError` while building, such as a feature missing from an older release, skips that codec instead of failing the client, so an application whose Jackson 3 is broken still runs on a working Jackson 2. When no codec is usable, `MemoryClient.create(...)` throws `MissingJsonCodecException` naming both coordinates and their floors, with each skipped codec's failure attached as a suppressed exception. `event=client.initialized` reports the outcome as `json=jackson3` or `json=jackson2`. The neutral selection code must not resolve either adapter or any Jackson type before the probe succeeds.

No configuration setting overrides the selection. Each adapter owns a privately configured mapper, never a framework's, and both are verified to behave identically, so which major serves a client is not observable on the wire. The only case an override would help is a present but broken major, which the fallback already handles. An override can be added later without breaking callers; withdrawing a public one could not.

The Jackson 2 adapter compiles against 2.19.0, the release LangChain4j 1.0.0 resolves. The Jackson 3 adapter now compiles against 3.1.4, the release Spring AI 2.0.0 resolves, still within the 3.1 LTS line that ADR 0003 chose. Both mappers ignore unknown properties, disable scalar coercion, read enums case-insensitively, reject numbers for enums, and write enums in lowercase. Both omit null-valued properties when encoding requests. Endpoint-specific private request records define outgoing shapes where public inputs do not match the wire contract; empty conversation metadata is mapped to null so it remains omitted. Wire DTOs continue binding `UUID`, enums, and public records such as `Message` and `Entity` directly; timestamps remain strings converted with `Instant.parse`, so the Jackson 2 adapter needs no JSR-310 module. One fixture suite runs against both codecs, the [ADR 0013](0013-validate-traffic-against-published-openapi.md) contract suite runs once per codec over the JDK transport, and classpath probes cover Jackson 3 only, Jackson 2 only with the LangChain4j transport, both majors, and neither. Running every transport against every codec was rejected because transports only move bytes. These checks close the parity risk recorded in ADR 0003. Converting wire DTOs to string-only fields was rejected as mapping code that guards against a risk the shared fixtures already detect.

Supported hosts are named by framework, and only verified ones are claimed: Spring AI 2.0+ (Jackson 3.1.4+ with Spring Framework 7.0+), LangChain4j 1.0+ (whose `langchain4j-core` brings Jackson 2.19+), and standalone applications that declare either major. Verification models each host by what the client touches, its Jackson databind and HTTP client, instead of depending on Spring AI artifacts: the LangChain4j transport's own dependency graph already supplies Jackson 2, and Spring AI 2 is modelled by Jackson 3 and `spring-web` at the versions Spring AI pins. The build compiles and tests at the floors. The README documents one `mvn test -D…` command that reruns the suite at the versions the newest supported releases resolve, Jackson 3.1.5 for Spring AI 2.0.1 and Jackson 2.22.1 for LangChain4j 1.22.0, and claims only the range that command covers. Spring AI 1.x and Spring Boot 3 applications may run on Jackson 2 with the JDK or LangChain4j transport but are not claimed. Floors are not enforced at runtime: any major whose mapper builds is selected, so Jackson 2.15 through 2.18 would run unverified. Refusing them was rejected because it would stop probably-working applications at startup and add a version check that the framework floors do not have.
